Three questions carry this whole lecture: what does a term look like, does it make sense,
and what does it do when it runs? That's syntax, typing, and semantics — the same three
questions every language in this app (and this course) answers, just with more machinery
added lecture by lecture.

<SectionHeading id="why-any-of-this" index="0" title="Why any of this?" blurb="A minute of context before the formalism starts." />

<ConceptSection id="what-is-stlc" title='What does "STLC" even mean?'>

STLC stands for **Simply Typed Lambda Calculus** — three words, three ideas, read right to left:

- **Lambda calculus** is the tiny language of functions this whole course is built on.
  `λ` is just the Greek letter Alonzo Church picked, in the 1930s, to mean "here comes a function."
- **Typed** means every piece of the program has to have one specific, checked-in-advance
  type — never a guess, never "we'll find out at runtime."
- **Simply** means the smallest useful version of "typed": no generics, no advanced tricks.
  Just enough to be real. Everything fancier (lectures 5–11) gets added on top, one idea at a time.

</ConceptSection>

<ConceptSection id="types-and-grammars" title="Types and grammars, in plain terms">

- A **type** is a promise about a value: "this is a `Bool`" means it's always `true` or
  `false`, never accidentally a number. **Type-checking** is just mechanically verifying
  every promise in a program is kept — before any of it runs.
- A **grammar** is a rulebook for what counts as a valid sentence — same idea as "the cat
  sat" being fine in English but "cat the sat" not. This lecture's grammar does that for
  terms: it decides which strings of symbols are even worth asking a type about.

</ConceptSection>

<ConceptSection id="where-this-comes-from" title="Where this comes from">

In 1901, Bertrand Russell found a contradiction sitting inside the foundations of
mathematics itself — a single sentence that was both true and false. It sent
mathematicians looking for a stricter answer to a question that suddenly seemed
urgent: what, exactly, counts as a valid computation?

Three people answered, independently, within a few years of each other — Kurt Gödel,
Alan Turing, and Alonzo Church, who happened to be Turing's own doctoral advisor.
Church's answer was a small notation for functions: the λ-calculus. All three turned
out to define the exact same thing, and Church's is the one TT builds on.

That's not just trivia. The question TT keeps asking, lecture after lecture — "does
this term make sense?" — is the same one TypeScript, Rust, or Java answers before your
code ever runs. Learn to answer it by hand, and a type error stops looking like a wall
and starts looking like a rule you can point to.

</ConceptSection>

<ConceptSection id="where-youll-see-this-again" title="Where you'll see this again">

Every statically-typed language you've used already runs a version of what TT
teaches — usually hidden behind a compiler. A handful of ideas worth naming now,
since you've likely met them already without the name:

- **Type inference** — TypeScript, Rust, and Kotlin guessing a type you didn't
  write — is the Γ ⊢ t : T judgement, solved automatically instead of checked
  against an annotation (lecture 8).
- **Generics** — explicit type parameters like `T` in Java, TypeScript, or Rust —
  are explicit polymorphism (lecture 9) with friendlier syntax.
- **Option/Result** types — the reason modern languages don't crash on null — are
  sum types (lecture 5) doing real work.

None of it needs memorizing here — just recognizing later, once you've seen the mechanism underneath it.

</ConceptSection>

<SectionHeading id="syntax" index="1" title="Syntax" blurb="What does a term look like, and what's its shape underneath?" />

<ConceptSection id="terms" title="Terms">

A **term** is just one piece of program text — think of it like a single LEGO
brick, or one ingredient in a recipe. On its own it's already a well-formed piece;
you build a whole program by snapping terms together. `5`, `true`, and `x` are all
terms by themselves; so is a whole function like `λx:Bool. x`.

Every term the app understands is built from just four shapes:

- `x` — a **variable**, standing for whatever it's bound to.
- `λx:T. t` — an **abstraction**: a function with parameter `x` of type `T` and body `t`.
- `t u` — an **application**: term `t` called with argument `u`. No symbol for
  "call" — you just write the two terms next to each other, with a space between.
  Chain three terms and it groups from the left, so `t u v` means `(t u) v` — call
  `t` with `u` first, then call whatever that gives back with `v`.
- `true`, `false`, numerals, and `if ... then ... else` — a small set of
  **constants** to actually compute with.

That's it — everything in later lectures (tuples, lists, recursive types,
polymorphism...) is more shapes added on top of these four. The full grammar
always lives on the [Grammar & Symbols](/docs/grammar) page; below is just the
slice this lecture uses.

</ConceptSection>

<ConceptSection id="the-arrow" title="The arrow: how a function's type is written">

`λx:T1. t2`'s type is written `T1 -> T2` — "a function that takes a `T1` and gives
back a `T2`". Think of it like a vending machine slot: put in exactly a `T1` (the
right coin), and you're guaranteed a `T2` back, no matter what happens inside.

`->` is **right-associative**, so `T1 -> T2 -> T3` means `T1 -> (T2 -> T3)` — "a
function that takes a `T1` and hands back *another function*, from `T2` to `T3`".
That's exactly what a multi-parameter function looks like once it's written as
nested single-parameter abstractions:

- `λ x : Bool . λ y : Bool . x` has type `Bool -> Bool -> Bool`, i.e.
  `Bool -> (Bool -> Bool)` — give it one `Bool`, get back a function still waiting
  for the second one.

Each arrow peels off exactly one argument — the same trick every curried function
in TS, Haskell, or Rust is built from.

</ConceptSection>

<GrammarBox grammar={`term ::= ID                                     (* variable *)
       | 'λ' ID ':' type '.' term               (* abstraction *)
       | term term                              (* application *)
       | term ('+'|'-'|'*'|'/') term             (* arithmetic *)
       | 'if' term 'then' term 'else' term
       | 'true' | 'false' | natural-number
       | '(' term ')'

type ::= ID | 'Bool' | 'Nat' | type '->' type          (* right-associative *)`} />

<ConceptSection id="text-to-tree" title="From text to tree">

What you type is **concrete syntax** — characters, spacing, parentheses. What the
parser hands to the typechecker and evaluator is **abstract syntax**: a tree with
the formatting stripped away, keeping only the shape. `(λ x : Bool . x) true` becomes:

- an **application** node, whose two children are —
- an **abstraction** node (parameter `x`, type `Bool`, body `x`), and
- a **literal** node (`true`).

Every rule from here on — typing rules, evaluation rules — is defined by matching
on this tree shape, not on the source text. The app's **AST** panel shows you this
tree live for whatever you type; try building the same tree by hand below, using
only the pieces introduced so far.

</ConceptSection>

<ConceptSection id="free-bound" title="Names: free vs. bound">

A variable occurrence is **bound** if it's inside the body of a `λ` that
introduces it, and **free** otherwise:

- `λx:Bool. x` — `x` is bound (by the outer `λx`).
- `λx:Bool. y` — `y` is free; nothing in the term binds it, so its meaning must
  come from outside (the context, Γ — covered in the next section).
- `λx:Bool. λy:Bool. x` — `x` is bound by the outer `λ`, `y` by the inner one.
  Both are bound; nothing is free.

</ConceptSection>

<ConceptSection id="alpha-equivalence" title="α-equivalence: names don't matter, bindings do">

A bound variable is just a placeholder for "whatever gets passed in" — renaming
it consistently throughout a term changes nothing about what it means:

- `λx:Bool. x` and `λy:Bool. y` — the *same* function, just spelled with a
  different parameter name. This is **α-equivalence**.
- `λx:Bool. y` and `λx:Bool. z` — genuinely *different* terms, since `y` and `z`
  are free and refer to two different things outside the term.

The rule of thumb: only which occurrences are bound *together* is meaningful — the label itself never is.

</ConceptSection>

<SectionHeading id="typing" index="2" title="Typing" blurb="Given the shape above, does this particular term make sense?" />

<ConceptSection id="why-bother" title="Why bother?">

The grammar above doesn't stop you from writing nonsense — applying a boolean as
if it were a function is syntactically fine, it just doesn't mean anything. Left
alone, a term like that gets **stuck** during evaluation: not a value, but no
rule applies to it either.

Typing catches this *before* anything runs, by answering one question for every
subterm: given what's in scope, does this make sense, and what does it produce?
That question has a name — the **typing judgement**:

<p className="text-center py-2 text-base text-foreground">`Γ ⊢ t : T`</p>

- Read it as "under context Γ, term `t` has type `T`".
- `Γ` (capital gamma) is the **context** — think of it as the list of parameters
  currently in scope, each paired with its type, the same way a function
  signature tells you what's available inside its body.
- A closed term (no free variables) can be checked against the empty context; a
  term with free variables needs Γ to say what they are.

</ConceptSection>

<ConceptSection id="how-to-read-a-rule" title="How to read a typing rule">

A rule is a recipe: a short list of things that must already be true — the
**premises**, above the line — and what follows if they are — the
**conclusion**, below it. No premises at all just means "always true".

</ConceptSection>

<SectionHeading id="semantics" index="3" title="Semantics" blurb="The term type-checks — now what does it actually do when it runs?" />

<ConceptSection id="math-functions" title="The same idea as ordinary functions">

Ordinary function notation and λ-notation say the same thing two ways:

- Math: `f(x) = x + 1`, then `f(3) = 4`.
- The app: `f = λ x : Nat . x + 1 : Nat -> Nat`, then `f 3` reduces to `4`.

"Calling `f` with `3`" and "replacing `x` with `3` throughout the body" are the
same operation. That replacement has a name — **β-reduction** — and, unlike the
informal math version, it's defined precisely enough for a computer to carry out.

</ConceptSection>

<ConceptSection id="substitution" title="Substitution, precisely">

**Substitution** is a fancy name for a simple idea: find-and-replace, like in a
text editor — swap every occurrence of one thing for another. Written `[x ↦ v]t`,
it means "`t`, with every free occurrence of `x` replaced by `v`". It's defined
by recursing over `t`'s shape — the same four shapes from the Syntax section:

- `[x ↦ v] x = v`
- `[x ↦ v] y = y`, if `y ≠ x` — leaves other variables alone.
- `[x ↦ v] (λy:T. t) = λy:T. [x ↦ v] t`, if `y ≠ x` — recurses into the body, as
  long as the inner binder doesn't shadow `x`.
- `[x ↦ v] (t₁ t₂) = ([x ↦ v] t₁) ([x ↦ v] t₂)` — recurses into both sides of an application.

β-reduction is exactly one application of this: `(λx:T. t) v → [x ↦ v] t`. For example:

<p className="text-center py-2 text-base text-foreground">`(λ x : Nat . x + 1) 3 → 3 + 1 → 4`</p>

</ConceptSection>

<ConceptSection id="evaluation-rule-meaning" title="What an evaluation rule means">

Typing rules ask "does this make sense"; evaluation rules ask "what happens
next". Each one is a **rewrite**: this exact shape becomes that shape, in one
step — like a single line of arithmetic, `2 + 2 → 4`. The arrow always means
"reduces to in one step", never "equals".

One more word shows up in the rules below: a **value** is just a term that's
already finished — nothing left to reduce. `true`, `5`, and any unapplied
function like `λx:Bool. x` are values; `3 + 1` is not — it can still be reduced, to `4`.

Two more rules round things out: reduce the function position first if it isn't
a value yet, then — once it is — reduce the argument. Together, these three
rules fully determine how any application runs:

<ConceptSection id="evaluation-strategies" title="Evaluation strategies: which redex first?">

A term can contain more than one reducible expression ("redex") at once — the
rules above don't say which one goes first. A **strategy** does. The app
supports three:

- **Call by value** (the default) — reduce an argument to a value *before*
  substituting it in. What most real languages do.
- **Call by name** — substitute the argument in unevaluated, and only reduce it
  once/if it's actually used. Never reduces under a `λ`.
- **Normal order** — always reduce the leftmost, outermost redex first,
  including under a `λ`.

The choice is observable: if a parameter is used more than once in the body,
call-by-name substitutes the unevaluated argument at *every* use and re-reduces
it each time, while call-by-value reduces it once, up front. Try the term below
under each strategy and compare the step counts:

</ConceptSection>

<ConceptSection id="non-termination" title="When evaluation never stops">

So far, every strategy just took a different *number* of steps to reach the same
answer. But not every term reaches an answer at all — some loop forever. Take the
untyped term `ω = λx. x x` — "a function that calls its argument on itself" — and
apply it to itself: `ω ω`. Substituting gives back `ω ω` again. And again. Forever.

Try to give `x x` a type in this lecture's language, though, and you get stuck:
`x` would need to be some type `T` *and* a function `T -> T2` at the same time —
plain STLC has no such type, so it never type-checks. That's not a coincidence —
it's a real theorem, **strong normalization**: every well-typed STLC term is
guaranteed to finish. (Lecture 7 reopens the door to loops on purpose, with a new
construct, `fix` — exactly because plain STLC can't do it by itself.)

Termination can even depend on the strategy: `(λx. y) ω ω` — a function that
ignores its argument and always returns `y`. Under call by name, `y` comes back
immediately, since the argument is never touched. Under call by value, the
argument is reduced *first*, before the function ever runs — and since `ω ω`
never finishes, neither does this.

</ConceptSection>

<ConceptSection id="church-rosser" title="Does the order ever change the answer?">

Strategies can disagree on speed, and — as above — on whether they finish at
all. But when two of them *do* both finish, they can never disagree on the
result. That guarantee is the **Church–Rosser theorem**: however many different
valid paths a term has, any two that reach a value reach the *same* value. Pick
any legal order of reductions you like — the answer, if there is one, was never in doubt.

</ConceptSection>
